# Набор тестов FreeToken

Каталоги соответствуют подсистемам `python/freetoken/`, которые тестирует каждый тест —
кладите новый тест рядом с модулем, который он защищает. Отдельного каталога под модели нет:
тест для конкретной модели живёт в той подсистеме, которую он нагружает, и указывает модель
в имени файла (`kvcache/test_dsv4_pool.py`, `models/test_glm4_nvfp4.py`).

| каталог      | тестируемая подсистема |
|--------------|------------------------|
| `daemon/`    | `freetoken.daemon` — супервизор без torch (безопасность импорта, менеджер serve) |
| `server/`    | `freetoken.server` — OpenAI/Anthropic/Responses API, стриминг, парсеры, учёт, состояние обслуживания |
| `scheduler/` | `freetoken.scheduler` — chunked prefill, менеджер кэша, блокировки commit/window, отчёт о статусе, использование KV, учёт стоимости |
| `kvcache/`   | `freetoken.kvcache` — пейджированные пулы (включая DSV4), перестройка, учёт стоимости кэша; три префиксных кэша живут в `kvcache/radix/` за общей эталонной моделью (см. её README) |
| `tokenizer/` | `freetoken.tokenizer` — обработка запросов tokenize/detokenize, разрешение thinking-режима |
| `engine/`    | `freetoken.engine` — планирование бюджета кэша, разрешение конфигурации, гейтинг бэкендов |
| `kernels/`   | `freetoken.kernel` / `freetoken.layers` — attention, rope, fused-операции, JIT-кэш, pinned memory |
| `moe/`       | `freetoken.moe` — offload-кэш, CPU/GPU-ядра экспертов, квантованные бэкенды (fp8/nvfp4/mxfp4/q4_0) |
| `models/`    | `freetoken.models` — реестр и загрузочная механика, общая для всех моделей (шардирование, qkv/expert merge, потоковая загрузка слоёв в банки) |
| `e2e/`       | проверки на реальном сервере: генерация AIME 24/25/26, перестройка кэша в рантайме |

Поверхность CLI сама по себе unit-тестами не покрыта. Диспетчеризация `ft`, `ft ctl`, `ft launch` и
`install.sh` тонкие, они часто меняются, а тест, написанный постфактум, лишь повторяет то,
что код делает сейчас — реальная проверка это запуск команды. Что здесь действительно живёт —
это логика, достижимая *через* эти команды, когда у неё есть собственный режим отказа:
`server/test_parser_auto_selection.py` покрывает вывод архитектуры -> парсера за флагом `--tool-call-parser auto`.

## Запуск

```bash
uv run pytest tests/                 # full suite, ~2-4 min on a GPU box
uv run pytest tests/ -m "not slow"   # skip the handful of tens-of-seconds tests
uv run pytest tests/kvcache/         # one subsystem
```

Тесты, зависящие от GPU, сами себя пропускают, если CUDA недоступна. Тесты Marlin NVFP4
пропускаются, если нельзя импортировать `vllm` (отдельный venv с `vllm>=0.14,<0.15`).

Тесты с пометкой `needs_weights` пропускаются, пока не задана переменная окружения,
указывающая на реальный локальный чекпоинт:

| переменная окружения       | используется |
|----------------------------|---------|
| `FREETOKEN_TEST_MODEL`     | `e2e/test_aime.py` — локальный каталог модели |
| `FREETOKEN_AIME_SERIES`    | `e2e/test_aime.py` — `aime24` \| `aime25` \| `aime26` (по умолчанию `aime25`) |
| `FREETOKEN_AIME{24,25,26}_JSONL` | `e2e/test_aime.py` — jsonl для выбранной серии |
| `FREETOKEN_AIME_REQ`       | `e2e/test_aime.py` — id задачи с 1, список через запятую (`1,3,7`) или `all` (по умолчанию `1`) |
| `FREETOKEN_AIME_MAX_TOKENS`| `e2e/test_aime.py` — бюджет токенов на один сэмпл (по умолчанию `16384`) |
| `FREETOKEN_AIME_SAMPLES`   | `e2e/test_aime.py` — число сэмплов pass@N при сэмплировании (по умолчанию `3`) |
| `FREETOKEN_AIME_MIN_FREE_GIB` | `e2e/test_aime.py` — требуемая свободная память GPU (по умолчанию `70`) |
| `FREETOKEN_TEST_MOE_CACHE_SIZE` | `e2e/test_aime.py` — >0 переключает на offload MoE-бэкенд с этим размером кэша |
| `FREETOKEN_TEST_MEM_RATIO` | `e2e/test_aime.py` — memory_ratio в offload-режиме (по умолчанию `0.9`) |
| `FREETOKEN_REBUILD_TEST_MODEL` | `e2e/test_cache_rebuild.py` — НЕБОЛЬШОЙ локальный каталог модели; поднимает реальный сервер (фолбэк на `FREETOKEN_TEST_MODEL`) |
| `FREETOKEN_GEMMA4_GGUF_GLOB` | `models/test_gemma4_gguf_rope.py` — glob, совпадающий с локальным файлом gemma-4 GGUF |

`test_aime.py` берёт протокол сэмплирования из собственного `generation_config.json`
чекпоинта (pass@N при рекомендованной температуре или один жадный сэмпл, если чекпоинт
рекомендует greedy). Чтобы запустить fp8 / offload-чекпоинт, укажите `FREETOKEN_TEST_MODEL`
на каталог fp8 и задайте `FREETOKEN_TEST_MOE_CACHE_SIZE=8192`; рецепт для offload —
`FREETOKEN_AIME_REQ=2 FREETOKEN_AIME_MAX_TOKENS=32768` (req 2 с бюджетом 32k).

Закладывайте лимит токенов под сэмплирование, а не под greedy: на Qwen3.5-35B-A3B-FP8 три
сэмпла рекомендованного сэмплирования aime25 req 1 потратили 4.1k / 10.7k / 10.0k токенов против
~4k у greedy, а req 2 требует ~21k даже жадно — отсюда бюджет 32k для более сложных задач.

Запускайте их перед открытием PR — они дешёвые, а проверка, которую никто не проваливает,
тихо гниёт:

```bash
FREETOKEN_REBUILD_TEST_MODEL=<small model dir> uv run pytest tests/e2e/test_cache_rebuild.py
```

## Что заслуживает места здесь

Тест должен уметь упасть на правдоподобной регрессии продакшн-кода.

Взвесьте это против того, как иначе нашлась бы ошибка. Поверхности, обращённые к приложению —
терминальный UI, фильтр access-log, кольцевой буфер запросов, эндпоинты статуса и здоровья,
CLI — объявляют о собственной поломке в момент, когда ими кто-то пользуется, и меняют форму
достаточно часто, чтобы unit-тест в основном повторял сегодняшнюю реализацию. Их место —
в `e2e/` и в реальном запуске. Unit-тест заслуживает логика, которая падает *молча*: неверное
число, которое всё ещё выглядит числом; семейство моделей, у которого тихо перестали
парситься tool calls; кэш, возвращающий не тот слот. Предпочитайте покрывать такое там,
где оно живёт, а не через поверхность, которая случайно его выставляет.

Писать тест в том же коммите, что и фича, правильно; важно, откуда берутся его ожидания.
Тест, который сверяет результат с чем-то независимым — PyTorch-эталоном, round-trip,
CPU-зеркалом, живым реестром — продолжает работать, когда реализацию переписывают, и может
с ней расходиться. Тест, чьи утверждения повторяют структуру ветвлений, которую автор только
что написал, может только соглашаться, поэтому он никогда не падает ни на чём, кроме
намеренного изменения, — и тогда его правят под новое. Если вы не можете назвать то,
*против чего* сверяется ожидание, тест вряд ли заслужит своё место.
Тесты-репродукции бага должны гонять текущий паттерн вызова исправленного кода, а не дофиксный;
тесты wire-формата и ядер должны утверждать против независимого эталона (round-trip,
dequant-оракул, CPU-зеркало), а не против собственного вывода реализации. Реестровые тесты
должны обходить живой реестр, а не поддерживаемые вручную whitelist'ы, чтобы новые записи
покрывались автоматически.
